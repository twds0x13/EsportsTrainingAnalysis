# 项目质量管控

## 目的

本规范指导智能体和开发者评估电竞训练分析系统的需求、架构、实现、测试与文档质量。审查结论以项目需求、代码、测试结果和可复现证据为依据，并为发现的问题给出明确处理方向。

## 基本原则

- **以项目目标为基准**：质量判断应结合课程设计范围、当前阶段、已确认需求和交付目标。保持工程高标准，不以项目规模为由忽略正确性、安全性、可维护性和可验证性。
- **证据支撑结论**：评价应关联具体需求、源文件、测试、构建结果、依赖关系或可复现操作。无法验证的内容标为待验证，不作已完成结论。
- **按阶段检查**：只应用当前阶段可验证的标准。设计阶段可以评审方案和待决事项；实现阶段检查行为与测试；交付阶段检查安装、部署、许可证和用户文档。
- **适用性优先**：不适用于本项目或当前阶段的标准标记为“不适用”，并简述原因。不要为了评分而虚构指标或证据。
- **建议可执行**：每项发现应说明位置或证据、影响、优先级和建议行动。区分已确认缺陷、待核实问题与可选改进。

## 质量维度

### 1. 需求与行为正确性

- 功能行为与 `memory/需求文档.md` 中已确认的需求一致。
- 需求、实现和测试之间可以追踪；尚未实现的需求不得描述为已交付。
- 待确认事项在受影响的设计或验收工作开始前得到明确处理，或被显式记录为当前决策及其影响。
- 性能、兼容性和安全性主张应有对应的测试、测量或权威资料支持。

### 2. 架构与模块边界

- 客户端和服务端实现位于 `src/` 下的独立区域，跨端共享内容仅承载明确的契约。
- 依赖方向清楚，模块职责明确；检查并避免循环依赖和不必要的跨层访问。
- 客户端训练逻辑、界面、输入、网络与持久化职责可辨识；服务端接口、应用逻辑、领域规则和基础设施职责可辨识。
- 评审架构时以项目实际需要为准。微服务、缓存、复杂抽象和额外基础设施必须有清晰需求或实测依据。

### 3. 数据与训练规则

重点验证以下需求不变量：

- 有效训练时间排除准备、倒计时准备、暂停和结果展示阶段。
- 暂停期间停止计时与采样；发生暂停的 session 按需求标记为无效，并记录原因。
- 网络断连产生的本地成绩与无效成绩分开处理；断网不改变已经完成的训练数据。
- 标准模式成绩能追溯到对应配置版本；修改标准参数或断网产生的成绩不进入全局排行榜。
- 点击分类、频率、命中率、反应耗时和准心覆盖率遵循需求文档中的定义。
- session 历史保留每次训练记录，并一致保存配置、原始指标、状态、失效原因和上传状态。

新发现的需求歧义应记录在需求或决策文档中。实现者不得通过猜测隐藏会影响训练结果、数据含义或排行榜资格的规则。

### 4. 测试与可验证性

- 核心训练规则、session 状态转换、时间统计、指标计算、离线成绩处理和排行榜资格应有针对性测试。
- 测试覆盖正常流程、边界条件和关键失败路径；覆盖率数字用于定位风险，不单独代表质量。
- 构建和测试结果应记录实际执行的项目、命令和结果。未运行的检查不得标为通过。
- 用户文档中的命令、示例和关键流程应在适用环境中实际验证。

### 5. 文档与可维护性

- 文档与当前实现及已批准决策一致，并明确区分已实现、计划中和待确认内容。
- 目录和命名应表达职责；新增文件优先归入已有责任模块，避免重复入口和无主文件。
- 代码和文档应便于后续维护，避免重复规则、隐式约定和无法验证的描述。
- 项目采用多语言文档或社区协作流程后，再纳入对应的同步和治理检查。

### 6. 安全、隐私与开源交付

- 账号认证、用户数据访问、成绩上传和服务端输入验证应结合具体实现进行检查。
- 不在仓库、日志或示例中暴露凭据、令牌或不必要的个人数据。
- 交付前确认许可证、第三方依赖许可、配置示例和部署说明符合项目交付范围。
- 安全问题按其实际影响和可利用条件优先处理，不以功能可用替代安全审查。

## 外部参考

当架构、测试、文档或工程流程存在需要比较的问题时，优先查询一手资料，并可参考 Vue、React、Node.js 等成熟开源项目的实践。引用前应确认资料与当前版本、具体问题和项目约束相关。

外部项目用于提供可借鉴的设计与验证方法，不构成所有维度的绝对评分基线。不得仅因某实践被大型项目采用，就认定它适合本项目；说明其适用条件及采用理由。

## 审查流程

1. **确定范围**：说明审查对象、项目阶段、适用需求和本轮不覆盖的内容。
2. **收集证据**：查看相关文档与代码，运行适用的构建、测试、静态检查或手动验证。
3. **核对行为**：将证据对照已确认需求及项目质量维度，检查数据、状态和接口边界。
4. **整理发现**：按影响排序，记录证据位置、复现条件、影响、处理建议及验证方式。
5. **总结状态**：分别列出已通过项、未解决问题、待验证事项和不适用项。需要修复时，先完成本地修复与验证，再报告结果。

## 发现优先级

- **阻断**：核心流程无法使用，数据错误或丢失，账号/数据安全存在重大风险，或交付条件无法满足。
- **高**：关键需求违反、训练结果或排行榜资格错误、主要平台构建失败，或缺少关键规则验证。
- **中**：局部功能、可维护性、文档或测试存在明确缺口，但核心数据与流程仍可用。
- **低**：影响有限的改进建议，不阻断当前阶段验收。

优先级应说明具体影响，不以代码行数、文件数量或主观印象定级。

## 质量审查报告

```markdown
# 质量审查：<范围>
- 日期：YYYY-MM-DD
- 阶段：需求 / 架构 / 实现 / 集成 / 交付
- 检查范围：<模块、需求或版本>

## 结论
<基于证据的简要状态；不使用无依据的综合分数>

## 发现
- [优先级] <问题与影响>
  - 证据：<文件、测试、命令结果或复现步骤>
  - 建议：<具体行动>

## 已验证
- <检查项及验证结果>

## 待验证 / 不适用
- <事项、原因及后续条件>
```

除非项目后续明确需要量化比较，否则使用证据和状态描述，不计算综合质量分数。单项指标（如测试通过率或覆盖率）应与其测量范围、方法和局限一并报告。
